# EyeLeo для macOS

**Версия 2.3.0.**

**English version of this document: [README.md](README.md).**

Нативный порт трей-приложения EyeLeo (Windows / C++ / wxWidgets): отсчитывает время до длинного
перерыва, предупреждает о нём и прерывает работу короткими упражнениями для глаз. Тот же автомат
состояний, те же возможности, те же формулировки — пересобрано на AppKit.

Приложение живёт только в строке меню: нет ни значка в доке, ни значка в переключателе приложений.

## Требования и загрузка

Готовые сборки рассчитаны на **macOS 13.0 и новее, как на Apple silicon, так и на Intel** —
публикуется универсальный бинарь. Сборка из исходников на вашей машине даёт бинарь под ту машину, на
которой идёт сборка, — для собственного Mac это обычно то, что нужно.

Готовые сборки лежат в каждом [релизе](https://github.com/defs-tech/eyeleo-mac/releases). Подписаны
ad-hoc, не нотарифицированы, потому что нотарификация требует платного аккаунта Apple Developer.
**Поэтому при первом запуске macOS будет возражать, и один раз его нужно пропустить**: правый клик по
приложению → «Открыть», либо «Системные настройки → Конфиденциальность и безопасность → Открыть всё
равно». Дальше оно работает как обычное приложение. Установщика `.dmg` нет: распакуйте архив и
перетащите приложение в `/Applications`.

## Что приложение делает

Всё, что делал оригинал 1.3.6, без изменений и целиком:

- строка меню: «Настройки», «Отключить перерывы на» (1 час / 3 часа), «Сделать длинный перерыв
  сейчас», «Открывать при входе», «Выход»;
- автомат состояний перенесён один в один, включая шестисекундную паузу «готовы ли вы» перед
  длинным перерывом, автоматический отдых после восьми минут бездействия, повтор при полноэкранном
  приложении, который сдаётся через пять минут, и продолжение отсчёта после перезапуска, если
  компьютер отсутствовал меньше тридцати минут;
- длинный перерыв: во весь экран, чёрный, леопард, сменяющаяся подсказка, часы, которые всегда
  показывают секунды, и кнопка «Пропустить», которую убирает тревожный режим;
- короткий перерыв: исходная панель `skin2` со случайным упражнением, анимацией, отсчётом,
  необязательным полноэкранным режимом и закрытием правым кликом, если включена соответствующая
  настройка;
- семь упражнений с правилом «никогда два раза подряд» и исходными таймингами анимаций;
- вехи на 30, 80, 120, 150, 400, 600, 1000 и 1400 коротких перерывах;
- пауза и возобновление, единственный экземпляр, статистика;
- английский и русский, с правильными формами множественного числа по-русски.

Добавлено в порту, коротко:

- **Ещё три упражнения** — с номерами 8, 9 и 10, у каждого пять формулировок на каждом языке.
- **Напоминание о воде** — по той же идее, что чайник, с семью сосудами и настраиваемой порцией.
  Только напоминает: ни ввода не забирает, ни клавиатуру не перехватывает.
- **Чайник с ручными проливами.** Семь чаёв с настоящими временами выдержки, и вода как ещё один вид
  напитка, поэтому «попить воды» и «заварить чай» — одно меню, а не две функции.
- **Звуки** по окончании перерыва и по окончании каждого пролива, под той галочкой, что уже была.
- **Тревожный режим** — убирает кнопку «Пропустить» и не даёт открыть меню во время перерыва.

Подробнее обо всём этом — ниже, в разделе [Что добавлено в порту](#что-добавлено-в-порту).

## Сборка и запуск

```
make            # build/EyeLeo.app, ad-hoc подписан и в песочнице
make test       # модульные тесты автомата состояний, без оконного сервера
make run        # собрать и запустить
make smoke      # сквозная проверка: тесты, локализация, значок в строке меню, оба цикла перерывов
make measure    # размер, холодный старт, расход памяти и сводка по безопасности
make install    # скопировать собранное приложение в /Applications
make uninstall  # убрать его оттуда
```

Нужны только инструменты командной строки из Xcode. Внешних зависимостей нет: ни CocoaPods, ни
Swift-пакетов, ни wxWidgets. pugixml тоже не нужен — оригинал использовал его только для чтения двух
небольших XML-файлов.

Две переменные меняют то, что собирается, и обе по умолчанию дают то, что нужно локальной сборке:
архитектуру этой машины и версию её системы.

```
make ARCHS="arm64 x86_64"          # универсальный бинарь вместо среза этой машины
make DEPLOYMENT_TARGET=13.0        # сборка под macOS 13 вместо 26
make ARCHS="arm64 x86_64" DEPLOYMENT_TARGET=13.0
```

Релизный workflow задаёт обе, потому что опубликованное приложение должно работать не только на машине,
которая его собрала. Ни то, ни другое не требует правки исходников: самый новый API здесь —
`SMAppService`, он появился в macOS 13, поэтому более низкая цель собирается без единого изменения, а в
SDK раннера есть оба среза для линковки. Важно, чего это *не* доказывает: что приложение собрано под 13
и линкует обе архитектуры, — факт, о котором сборка сообщает; что оно корректно работает на macOS 13 или
на Intel, — это может показать только запуск там.

## Установка

```
make install                  # собрать, затем скопировать build/EyeLeo.app в /Applications
open /Applications/EyeLeo.app
make uninstall                # убрать обратно
```

Установщика `.dmg` нет: подписанный ad-hoc бандл, который пользователь перетаскивает в
`/Applications`, — это и есть вся раздача, поэтому `make install` копирует, а не упаковывает. Путь
можно переопределить, чтобы проверить цель не трогая систему: `make install DESTDIR=/tmp/check`.

Три детали в этой цели не случайны. Она отказывается работать, пока EyeLeo запущен, потому что
приложение молча выходит при втором экземпляре, а перезапись каталога под живым процессом оставляет
его читать бандл, которого уже нет; проверка ищет исполняемый файл внутри любого бандла, поэтому
ловит и запущенную копию из `build/`, и из `/Applications`. Старый бандл удаляется до копирования,
потому что `ditto` сливается с существующим каталогом и иначе оставил бы файлы, которых в новой сборке
уже нет. И после копирования проверяется подпись — именно копирование может её сломать.

Если в `/Applications` нет прав, предлагается `sudo ditto build/EyeLeo.app
/Applications/EyeLeo.app`, а не `sudo make install`, и это намеренно: второе собрало бы от root и
оставило бы в `build/` файлы, принадлежащие root.

Настройки и `tea.conf` лежат в `~/.config/eyeleo-mac`. Раньше они были в контейнере песочницы, на
четыре уровня вглубь под именем от идентификатора бандла, — плохое место, чтобы просить кого-то держать
там расписание чаёв. Перенос стоит приложению одного исключения песочницы, оно объявлено в
`entitlements.plist` и ограничено одним этим каталогом; подробности в `docs/tea.md`.
`make uninstall` этот каталог намеренно не удаляет.

Включайте **«Открывать при входе»**, только когда приложение уже в `/Applications`. Оно регистрирует
главный бандл через `SMAppService`, а бандл, лежащий в `build/`, LaunchServices надёжно не регистрирует.

Учтите, что `make run` запускает копию из `build/`, поэтому запуск при уже работающей установленной
копии — ровно тот случай с двумя экземплярами, о котором предупреждает проверка выше.

**`build/EyeLeo.app` показывается как второй EyeLeo.** macOS регистрирует приложение при первом запуске,
а LaunchServices не забывает ничего: папку удалили, а имя осталось в «Программах», пока кто-нибудь его
не снимет. Здесь их набралось четыре — установленная копия, копия в `build/` и две, чьи папки давно
исчезли. `make clean` убирает папку, но не имя:

```
LSREG=/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister
"$LSREG" -u /полный/путь/к/EyeLeo.app
```

Стоит делать, только если остаток раздражает. Каждая сборка возвращает запись обратно.

## Почему Objective-C, а не Swift

Задача ставилась так, чтобы footprint был минимальным, а он определяется языком, а не микрооптимизацией.
Swift тащит в каждый процесс `libswiftCore` и метаданные среды выполнения; SwiftUI добавляет
собственных несколько мегабайт. Ни то, ни другое потом не вернуть. Objective-C с AppKit — это пол для
утилиты в строке меню: 200 КБ бинарника и никакой среды выполнения.

SwiftUI не используется вовсе. Окно настроек — обычные представления AppKit в `NSStackView`.

## Измеренные результаты

Из `make measure` на MacBook Air с M2:

| Метрика | Измерено | Бюджет |
| --- | --- | --- |
| Бинарь | 202 КБ | 3 МБ |
| Бандл с ресурсами | 1,7 МБ | — |
| Холодный старт до готовности | ~140 мс | 500 мс |
| `phys_footprint` в покое | 10 МБ | 12 МБ |
| `phys_footprint` во время перерыва | 13 МБ | 25 МБ |

Собственный вклад приложения в старт — около 75 мс, остальное измеренного окна приходится на создание
процесса. Оверлеи создаются по требованию и уничтожаются вместе с перерывом, поэтому простаивающий
EyeLeo не держит ни окон, ни декодированных картинок.

Почему расход памяти остаётся небольшим:

- по одному `dispatch_source` на задачу (автомат, 100-мс тик оверлеев, секундный тик, затухание), а не
  по таймеру на окно, как в оригинале;
- монотонный `clock_gettime` вместо выделения `NSDate` на каждый тик;
- текст отсчёта форматируется через `snprintf` и превращается в `NSString` только когда видимая строка
  действительно меняется, раз в секунду, а не десять раз;
- декодированные изображения освобождаются по окончании перерыва;
- `-Os`, `-fvisibility=hidden`, `-Wl,-dead_strip`, бинарь стрипнут.

## Безопасность

Приложение **ничего** не запрашивает у системы. Диалог разрешений не может появиться, потому что не
вызывается ни один API, который его вызывает.

- App Sandbox. В `entitlements.plist` ровно две возможности: `com.apple.security.app-sandbox` и
  исключение на один каталог `~/.config/eyeleo-mac`, где лежат настройки и расписание чаёв. Второе
  появилось, когда файлы переехали из контейнера наружу; иначе их нельзя было бы открыть и отредактировать,
  а это ровно то, для чего они существуют. Ни сетевого клиента, ни камеры, ни микрофона.
- Сетевые символы вообще не линкуются (`make measure` это проверяет), так что оно не позвонит домой,
  даже если в будущей правке попытается.
- Оригинал перехватывал мышь и клавиатуру глобально. На macOS это означало бы разрешение Accessibility
  или Input Monitoring. Вместо этого активность читается через
  `CGEventSourceSecondsSinceLastEventType(kCGEventSourceStateCombinedSessionState, ...)`, что даёт
  активность за всю сессию без всяких разрешений. Полноэкранные приложения определяются через
  `CGWindowListCopyWindowInfo`, который отдаёт границы окон без разрешения Screen Recording.
- Уведомления рисуются собственным пузырём приложения, а не через `UNUserNotificationCenter`, который
  потребовал бы разрешения Notifications.
- На диск пишутся только два файла, `tea.conf` и `settings.xml`, оба в `~/.config/eyeleo-mac`. Файла
  журнала нет: оригинал открывал и закрывал `log.txt` на каждое сообщение, что и медленно, и тихо
  документировало, когда вы работали. Диагностика идёт в `stderr` и появляется только под
  `EYELEO_DEBUG=1`, то есть когда её явно попросили.
- Подписано ad-hoc (`codesign -s -`). `codesign --verify --strict` проходит. Не нотарифицировано, что
  для приватной сборки нормально, но означает, что Gatekeeper возразит при переносе на другой Mac.

`make measure` перепроверяет возможности и сетевые символы, так что будущая правка, расширяющая
поверхность, громко провалится в отчёте, а не тихо.

## Что добавлено в порту

В оригинале было семь упражнений, и для упражнений 1..7 так и осталось: те же номера, те же
формулировки на обоих языках, та же графика. Ничего не убрано и не переписано. Добавлено было пять
вещей.

**Три упражнения, номера 8, 9 и 10.** «Полностью и мягко закройте глаза, десять раз» держит кадр с
закрытыми глазами дольше открытого, потому что смысл в полном неторопливом моргании, а не в быстром.
«Поднимите и опустите плечи» — бюст леопарда с плечами вверх и вниз, «закройте глаза обеи лапами»
чередует открытые глаза и глаза за обеими лапами. Все три нарисованы кадрами, как и все остальные, и
у каждого по пять формулировок на язык.

**Теперь у каждого анимированного упражнения настоящая графика.** Это главное разворот в порту.
Плечи сначала анимировались кодом: два наложенных слоя, голова и торс, двигаемые через
`CATransform3D`, — на том основании, что одна сгенерированная пара выйдет несогласованной и точки на
меху поползут по шерсти. Рассуждение было верным про поломку и неверным про лечение. Два слоя давали
скользящую картинку вместо движения, и расхождение между поворачивающейся головой и поднимающимся
торсом читалось как плохой монтаж, а не как тело.

Лечение оказалось в инструменте, а не в анимации. `tools/mkframes.m` выравнивает каждый сгенерированный
кадр набора по измеримым опорам внутри картинки, так что пара кадров согласована по построению, а не по
надежде; `CATransform3D` теперь тождественна для каждого упражнения, а `transform` осталась только
ради честности заголовка. Точки не ползут, потому что оба кадра мерились по одной и той же опоре.

У `tools/mkframes.m` пять режимов: `full`, `bust`, `eyes`, `shoulders` и `cups`. Он убирает плоский фон
по мадженте, отбрасывает случайные пиксели внутри выделенной области, пересемплирует усреднением по
площади, выравнивает кадры набора и отказывается писать что-либо, чей размер расходится с соседним или
у чей прозрачность ненастоящая. Заодно он пишет `preview_*.png`, отрисованные на тёмном фоне самой
панели: оценивать маленькую фигуру на глаз в таком окружении оказалось многократно обманчиво, и
несколько кругов «ассет в порядке, панель не та» сводились к тому, что видно только на том фоне, на
котором фигуре и стоять.

Бюст для упражнения с плечами вырезан из той же картинки, что и длинный перерыв, а не сгенерирован
заново, чтобы лицо у них было одно. Он 276x220 px, показывается как 138x110 pt. Сгенерированные кадры
не несут метаданных DPI, поэтому `EBAssets` уменьшает их вдвое при загрузке: всё начиная с
`EBFrameShouldersUp` — вдвое больше исходных кадров 1x, а семь унаследованных — 1x. Ошибка в любую
сторону либо удваивает картинку, либо уменьшает её до размера миниатюры.

**Длинный перерыв двигается настоящими кадрами.** Это был единственный экран без движения вовсе. Он
проводит фигуру в полный рост через четыре позы: стоя, наклон влево, стоя, наклон вправо, по две
секунды каждая, так что полное покачивание занимает восемь секунд. Все четыре сгенерированы тем же
инструментом, что и упражнения, и выровнены по тем же опорам.

Чтобы их согласовать, одной ограничивающей рамки не хватило. Наклонённые позы выбрасывают поднятую
руку за пределы фигуры, так что по рамке наклонённые кадры выходили больше стоящих, а масштабирование
всех четырёх по рамке заставляло стоящую фигуру сжиматься посреди собственного цикла. Инструмент
нормирует по ширине икры, потому что она единственная остаётся на месте во всех позах. В итоге фигура
занимает 155x340 pt на дисплее 1470x956.

Попытка сгенерировать фигуру в полный рост была раньше и дала четвероного, поэтому первая версия этого
экрана переиспользовала бюст и покачивала его кодом. Кадры теперь есть, значит покачивание рисуется.

**Напоминание о воде.** Тот же пузырь на `skin4`, тот же правый нижний угол, те же 209x71, что и у
отсчёта до длинного перерыва, и теперь то же для чая — только вместо портрета сосуд. Это нарисованная
картинка, а не кодовый стакан: семь чашек, вырезанных режимом `cups` инструмента `tools/mkframes.m`,
который сохраняет их настоящую прозрачность вместо обрезки по плоскому фону. Только напоминает: ввода
не забирает и клавиатуру не перехватывает.

Цифры за ним. Показатель 15-20 минут из рекомендаций по охране здоровья относится к работе в жару, где
потеря пота реальна; на сидячую работу он не переносится. Релевантное исследование по офисным
работникам (PMC8998380) нашло базовый уровень около 763 мл в сутки и проверяло опросник на интервалах
30-60 минут, а не 15-20. Поэтому по умолчанию стоит 30 минут и 100 мл: это всё ещё 200 мл в час, но
приходят двумя глотками, а не одним стаканом на 200 мл, — это и есть то, что NIOSH имеет в виду,
предпочитая короткие интервалы большим редким объёмам.

Напоминание считает только время работы: оно уменьшается внутри ветки простоя, поэтому перерыв его
приостанавливает, а не копит напоминания против того, кто отошёл от стола. Оно также не срабатывает,
пока приложение в автоматическом отдыхе, — после восьми минут простоя там находится любая машина, за
которой никто не сидит. Оба решения осознанные, и о них стоит знать при проверке: пятнадцатиминутный
тест на машине, которую никто не трогал, напоминания не покажет, потому что автоматический отдых
приходит на восьмой минуте.

Список интервалов — 15/20/25/30/45/60/90/120, список порций — 50-250 мл. Худшее сочетание из этих двух
списков, 15 минут по 250 мл, даёт 1000 мл в час против потолка в 1414 мл/час, выше которого NIOSH
предупреждает о водной интоксикации. Ни одна комбинация настроек этот потолок не превышает, и на
это есть проверка.

**Чайник, который расширяется правкой текстового файла.** Тот же пузырь, тот же отсчёт, а список чаёв
берётся из `tea.conf`. Имя в строке — это вся личность чая: по нему ищется файл картинки, и оно же
показывается в меню, если для чая нет перевода. Добавленная строка добавляет пункт меню, без
пересборки и без регистрации где-либо ещё.

```text
# имя, температура в °C, дальше по одному времени пролива, в секундах
green, 80, 10, 15, 20, 25, 30, 35
jasmine, 85, 30, 45, 60
```

Меню следует за файлом: первая строка — первый пункт, так что перенос строки переносит пункт, а чаёв,
которые не перечислены, просто нет. `tea.conf` лежит в `~/.config/eyeleo-mac`, и приложение его больше
никогда не переписывает.

Подписи пишутся в той же строке, как `en="..."` и `ru="..."`. У чая, у которого их нет, показывается
имя из файла, а подпись на языке, которого у сборки нет, отбрасывается, и чай остаётся.

В корне этого репозитория лежит `tea.conf` с шаблоном, и он попадает в бандл. При первом запуске,
если файла в `~/.config/eyeleo-mac` ещё нет, он создаётся из этого шаблона — один раз, и никогда
поверх существующего. Так же устроено и в сборке для Windows уже несколько версий, и это то,
из-за чего файл не приходится создавать вслепую. Файлы со старого места в контейнере переносятся
автоматически, один раз, при первом запуске после обновления.

Семь чаёв идут с обычным временем выдержки: белый и зелёный 10-15-20-25-30, улун 15-25-35-45-60-75,
чёрный 20-30-40-50-60-70, красный 7-10-15-20-25-30 при 95 °C, пуэр 20-30-40-50-60-70-80-90 и травяной
300-360-420-480. Это же и запасной вариант: пустой или целиком негодный `tea.conf` даёт встроенные
расписания, так что приложение работает даже с испорченным файлом.

**Что требуется от строки.** Всё это проверяется, а не предполагается, и строка берётся целиком или
отвергается целиком: наполовину прочитанного расписания не бывает, и после неудачной строки не
остаётся лишнего пролива.

| Поле | Правило |
| --- | --- |
| имя | одно слово без пробелов: строчная латинская буква, дальше буквы, цифры или подчёркивание, до 24 знаков |
| температура | число больше 0 и не больше 100 |
| проливы | от 1 до 8 времён, каждое целым числом секунд от 1 до 3600 |

Регистр не сворачивается, а отвергается. Том на macOS по умолчанию нечувствителен к регистру, поэтому
`Tea.png` и `tea.png` — один файл, и имя, отличающееся только регистром, молча подхватило бы чужую
картинку. По той же причине длина ограничена 24 знаками: имя становится именем файла, а имя файла,
которое может дойти до конца пути, не такое уж приятно получать из текстового файла.

Восемь проливов — потолок, а не произвольное число: это длина самого длинного расписания из
поставляемых, пуэрского. Повтор имени оставляет первое определение и отвергает второе, так что старый
блок строк, вставленный ниже, не перебивает расписание молча. Одна плохая строка выбрасывается, а
остальной файл всё равно используется; к встроенным чаям откатывается только файл, в котором не
годного нет ничего.

**Подпись пишется в той же строке чая**, как `en="..."` и `ru="..."`, а имя из `tea.conf` — запасной
вариант для языка, у которого подписи нет. Именно запасной, а не пустая строка, чтобы добавленный чай
был читаем до того, как для него что-то напишут. Подпись в кавычках, потому что в названии может быть
запятая, а разделителем полей считается только запятая вне кавычек. Языковые пакеты тут ни при чём:
ключ в них подпись на строке не перекрывает, а `tea_name_*` не читается вовсе.

**Сосуд у каждого чая, а у кого-то его нет.** Чай рисует `tea_<name>.png`, проверяемый при загрузке:
PNG, 8 бит на канал, тип цвета 6, то есть с настоящим альфа-каналом, и не больше 142×88 px — это
угол пузыря 71×44 pt в 2×. Не прошедшее отвергается, место остаётся пустым, причина в журнал. Чай
без картинки всё равно заваривается, просто без стакана.

Выдерживание намеренно ручное. Автоматический таймер не может знать, когда вы уже слили воду с листа,
поэтому отсчёт врал бы всем, кто отвлёкся, и лечится это кнопкой, а не более хитрым предположением.
Пункт меню отсчитывает время до следующего пролива, пузырь исчезает, как только пролив сделан, а после
последнего пузырь сообщает, что чай заварился, и закрывается сам через пять секунд. Подсказки в меню
показывают всё расписание чая сразу, поэтому выбирать между ними не приходится заваривать.

**Вода — не чай.** У неё нет расписания проливов, её нет в `tea.conf`, и никакая строка оттуда не
выведет её в меню. Вода — это напоминание выше, со своими настройками и своим стаканом: отдельная
функция, которая просто делит с чаем пузырь.

Две вещи таймер не делает. Он не останавливается на перерыве, потому что пролив, вставший на паузу, пока
человек смотрит в экран, — это ошибка, а не вежливость; и он не запоминает выбранный чай при следующем
запуске, так что галочка относится только к текущей сессии. Оба — решения, а не пропуски.

Верно и наоборот. Пока идёт пролив, короткий перерыв, напоминание о воде и длинный перерыв ждут: всё
четыре не показывается и ничто не кладётся поверх отсчёта заваривания. Пролив короткий — тридцать
секунд у зелёного, полторы минуты у пуэра, — и задержать перерыв ради почти закончившегося отсчёта
ничего не стоит. Как только проливу остаётся больше двух с половиной минут, держать он больше не может.
Это расписание травяного чая, проливы по пять-восемь минут: там побеждает приложение, перерыв приходит
как положено, а пузырь с завариванием убирается до его конца. Сама сессия при этом не теряется никогда.

## Чтение настроек, записанных другими инструментами

`PutBool` пишет 0/1, то есть собственные файлы приложения хранят числа там, где ожидается флаг. Это
означало, что `ReadBool`, проходивший через числовой чтец, молча игнорировал любой `<true/>` или
`<false/>` — а именно так plist пишут `defaults`, `PlistBuddy` и всё, что правит файл как XML.
Симптом был флажок, который сам включался обратно. Теперь принимаются обе записи, и есть проверка,
которая пишет plist с настоящими логическими значениями и убеждается, что `<false/>` читается как
ложь, а не как отсутствие.

Пока настройки шли через `CFPreferences`, прямая запись файла, даже через `plistlib`, ничего не меняла
наблюдаемо: чтение обслуживалось из кэша `cfprefsd`. Теперь это обычный файл, и правка его видна сразу.
## Двухступенчатое предупреждение перед длинным перерывом

Уведомление и предложение отложить — это два разных такта, примерно в 24 секунды реального
времени:

1. Пузырь в правом нижнем углу появляется, когда `timeLeftToBigPause` опускается до
   `warningInterval` — по умолчанию 30 секунд — и отсчитывает. В этот момент остаток принудительно
   приравнивается ровно к `warningInterval`, чтобы пузырь всегда начинался с круглого числа.
2. Диалог по центру с тремя кнопками появляется, когда `timeLeftToBigPause` опускается до
   `EBLongBreakConfirmationSec` — 6 секунд — и отсчитывает с 6 до 0, прежде чем принять клик.

Именно так делал оригинал под Windows: пузырь начинается за 30 секунд и всё ещё тикает с оставшимися
пятью секундами, когда диалог открывается поверх него.

Если вы когда-нибудь увидите, что оба пришли одновременно, у вас включён `EYELEO_FAST_MODE=1`. Он
умножает прошедшее время на 8 для длинного перерыва, так что разрыв в 24 секунды схлопывается примерно
до трёх, пока собственные шесть секунд диалога идут в настоящих секундах. Пороги тут ни при чём.

У `warningInterval` есть нижний предел в 20 секунд — самое короткое ожидание, которое предлагает окно
настроек; проверяется в `clampSettings`. Окно предлагает только 20/30/60/90 секунд, так что предел
существует для файла настроек, который правили руками или который испортился: ниже 6 секунд
уведомлению не было бы совсем времени на отсчёт.

## Захват клавиатуры и мыши во время перерыва

Задача требовала, чтобы перерыв действительно останавливал работу: затемнить экран и забрать клавиатуру
с мышью, чтобы человек правда отдохнул. Это сделано, с одной честной оговоркой.

**Мышь — обработана полностью и проверена.** На всё время перерыва поверх всех остальных приложений
поднимается прозрачное окно во весь экран, в том числе над самой панелью. Клики и прокрутка в любом месте
экрана попадают в наше окно и дальше не идут. У длинного перерыва оверлей и так закрывает весь экран; у
короткого именно этот отдельный щит не даёт работать дальше вокруг панели 461x156.

**Клавиатура — работает, проверено.** Приложение только из фоновой категории (`LSUIElement`) никогда не
получает фокус клавиатуры: приложение на переднем плане остаётся тем, чем было, и нажатия продолжают
уходить в редактор, а перерыв был бы декоративным. Единственный публичный путь — на время перерыва
поднять политику активации до `Regular`, активироваться и сделать оверлей ключевым окном, что код и
делает; это тот же бой, что в оригинале вели с `BigPauseWindow::_restoreFocus`. Цена — значок в доке и
меню приложения, пока перерыв на экране; после исчезают оба.

Измерено, при `EYELEO_DEBUG=1`:

```
[EB] capture input: appActive=0 key=0 windows=2
[EB] capture settled: appActive=1 key=1 main=0 front=local.eyeleo.EyeLeo
[EB] restore focus to "NyaTerm"
```

Первая строка — момент вызова, до того как система закончила активацию; вторая — через 400 мс и
показывает приложение на переднем плане с оверлеем как ключевым окном, что и отводит клавиатуру.
Третья — фокус возвращается тому, чем вы занимались. Второй перерыв ведёт себя так же, между циклами
ничего не течёт.

Альтернатива — `CGEventTap`, съедающий события клавиш, — гарантировала бы блокировку, но требует
разрешения Accessibility и сломала бы свойство «ничего не просит», описанное выше. Этот компромисс не
принят.

## Грабли, о которых стоит знать

- **Сгенерированная иконка может оказаться молча пустой.** `mkicon.m` масштабировал CTM контекста
  растрового изображения на размер в пикселях, пока код рисования работал в пиксельных координатах,
  поэтому каждый глиф приземлялся далеко за пределы холста. PNG были корректны, грузились, сообщали
  `isTemplate = YES` и не рисовали *ничего* — отсюда первая версия значка в строке меню была невидима,
  хотя `isVisible` был `YES`, а кнопка стояла правильно. Теперь `mkicon.m` отказывается писать глиф, в
  котором нет непрозрачных пикселей.
- **Картинки в строке меню должны быть 22 pt, а не 44.** `NSStatusBar.thickness` на этой машине
  равен 22 pt, а `NSImage` читает голый PNG как «пиксели равны пунктам». Поэтому единственный ассет
  44x44 становится картинкой 44 pt и кнопка схлопывается до `38x0`. Обе масштабировки должны
  поставляться, `StatusActive.png` размером 22x22 и `StatusActive@2x.png` размером 44x44, и
  загружаться через `+[NSImage imageNamed:]`, чтобы разрешился `@2x`.
- **AppKit отсчитывает снизу.** В вёрстке Windows координаты шли от левого верхнего угла, так что буквальный
  перенос помещал картинку упражнения в `y = -70`, свисая с низа панели и поверх заголовка. Теперь
  раскладка панели выражена один раз в координатах AppKit.
- **Опрашивайте правильное окно.** Короткий перерыв кладёт щит от кликов в список окон *до* панели, и
  щит намеренно никогда не ключевой. Проверка `firstObject.isKeyWindow` даёт ложный отрицательный
  ответ; ввод перехватывает панель.
- **Таймеры не должны делить цепочку приоритетов.** Один dispatch-таймер на все оверлеи, упорядоченный
  по важности, позволяет секундному отсчёту проглотить сотомиллисекундный — и диалог «готовы ли вы»
  перестаёт отсчитывать. Два таймера, по одному на частоту.
- **`NSAnimationContext` здесь ненадёжен.** Затухание альфы окна через прокси `animator` не
  завершается у неактивного `LSUIElement`-приложения, так что обработчик завершения не вызывался и
  короткий перерыв не закрывался сам. Затухание теперь шагается собственным таймером.

## Запуск и как на это смотреть

```
make                      # собрать и подписать build/EyeLeo.app
open build/EyeLeo.app     # только строка меню, без значка в доке
```

Чтобы увидеть одно конкретное упражнение, а не ждать его в одном розыгрыше из десяти:

```
EYELEO_DEBUG=1 EYELEO_FAST_MODE=1 \
EYELEO_TEST_INTERVAL_MIN=1 EYELEO_TEST_ONLY=short EYELEO_TEST_EXERCISE=9 \
  ./build/EyeLeo.app/Contents/MacOS/EyeLeo
```

Запуск бинаря напрямую, а не через `open`, сделан намеренно: только так до него доходит `EYELEO_DEBUG`.
В отладочном режиме трассировка печатает раскладку панели, и по ней проверяется размещение графики:
картинка, заголовок и отсчёт печатаются каждый со своими рамками, и неверный размер там означает, что
упражнение открылось на кадре другого размера.

Напоминание о воде — единственное, до чего иначе не добраться быстро, потому что его интервал упирается
в пятнадцать минут:

```
EYELEO_DEBUG=1 EYELEO_TEST_WATER_SEC=6 ./build/EyeLeo.app/Contents/MacOS/EyeLeo
```

## Отладочные переменные и тестовые крючки

Всё выключено, пока переменная окружения не задана. `EYELEO_DEBUG` дополнительно трассирует каждое
переключение состояний.

Это же место, где чай, который не появился, получает своё объяснение, и единственное. Проблемы с
`tea.conf` сообщаются здесь и больше нигде, намеренно: отвергнутая строка — это ошибка в файле, который
никто не должен править рукой, а понадобится он тому, кто как раз правит. Так что если добавленного
чая нет в меню, запустите с `EYELEO_DEBUG=1` и прочитайте, что приложение написало про вашу строку.

| Переменная | Действие |
| --- | --- |
| `EYELEO_DEBUG=1` | трассировка автомата, этапов старта, оверлеев и каждой отвергнутой строки `tea.conf` с причиной |
| `EYELEO_FAST_MODE=1` | ускоряет таймеры до 8×, порт `EyeApp::_fastMode` |
| `EYELEO_TEST_INTERVAL_MIN=N` | переопределяет оба интервала перерывов на N минут |
| `EYELEO_TEST_ONLY=short\|long` | включает только один вид перерыва |
| `EYELEO_TEST_EXERCISE=N` | принудительно ставит упражнение N на следующем коротком перерыве |
| `EYELEO_TEST_OPEN_SETTINGS=1` | открывает окно настроек при запуске |
| `EYELEO_TEST_WATER_SEC=N` | показывает напоминание о воде через N секунд |
| `EYELEO_TEST_TEA_SEC=N` | показывает пузырь чая через N секунд |
| `EYELEO_TEST_TEA_NAME=name` | какой чай показывается в пузыре, по имени из `tea.conf` |

Переопределения намеренно бьют сохранённые настройки — в то время это было как раз нужно: `cfprefsd`
кэшировал предпочтения по приложению, и правка файла из шелла не была надёжно видна приложению в
песочнице. Поэтому они существуют, а не шаг с правкой файла настроек в инструкции.

Пока активна любая из `EYELEO_TEST_*`, приложение выставляет `persistenceSuspended`, и `saveSettings`
становится пустым. Без этого ускоренный прогон переписывал бы интервалы перерывов в настоящие
настройки на каждом перерыве, а это ровно тот ущерб, который тест делать не должен.

## Затемнение во время перерыва

Каждый перерыв устроен одинаково: под ним во весь экран слой затемнения, поверх — непрозрачное окно с
содержимым.

Оба перерыва затемняют экран одинаково: чёрным при альфе **0.78**, без размытия. Значение подбиралось
на глаз — 0.62 и затем 0.90 описывали как нечитаемо тёмные, 0.78 как правильное, — и короткий перерыв
подровняли к нему.

Заднего размытия нет. Его пробовали и убрали: `NSVisualEffectMaterialHUDWindow` сам по себе тёмный
материал, поэтому он расплющивал всё за оверлеем ещё до применения слоя затемнения, и даже светлый
вариант читался тяжелее, чем простой слой длинного перерыва. Оставлять галочку, которая ничего не
делает, было бы хуже, поэтому настройку убрали, а не оставили мёртвой.

Прозрачен только слой затемнения. Картинка упражнения, текст, часы и кнопки затемняются до полной
непрозрачности — сборка Windows анимировала свои окна до 210/255, что на macOS затемнило бы содержимое
вместе с рабочим столом. Слой затемнения же — это то, что съедает клики, адресованные тому, над чем вы
работали.

Слой затемнения стоит **на одно окно ниже** содержимого (`NSFloatingWindowLevel - 1` против
`NSFloatingWindowLevel`). В пределах одного уровня клик по окну выводит его в начало этого уровня, так
что клик где угодно вне панели упражнения раньше задвигал панель за слой затемнения. Разные уровни делают
порядок абсолютным, а не зависящим от того, куда кликнули, при этом слой всё ещё выше обычных окон
приложений и продолжает съедать их клики.

Кнопкам задаётся явный непрозрачный `bezelColor`. На прозрачном окне поверх затемнённого рабочего стола
штатный скруглённый бейз рисуется со своей прозрачностью и читается как полупрозрачный, отчего кнопка
«Пропустить» выглядела бледной рядом с полностью непрозрачными текстом и графикой.

Панели рисуются, а не выводятся картинкой. У PNG `skin2/skin3/skin4` из сборки Windows есть сплошная
белая рамка, которая была маской формы окна (`SetShape(region(bitmap, *wxWHITE))`) и рисовать её никто
не собирался; отрисовка их на macOS давала белую обводку вокруг каждой панели. Они по-прежнему нужны
ради размеров, а тёмный скруглённый фон рисуется вместо них.

## Две грабли

**Пузырь с отсчётом надо ставить по `visibleFrame`, а не по `frame`.** Уведомление о длинном перерыве
раньше позиционировалось по всему дисплею и начиналось в `y=0`, где находится док. На доке в 60 pt из его
71 пункта шестьдесят были под панелью и видна была только верхняя кромка. Теперь все плавающие
оверлеи идут через `EBBottomRightRect` или `EBCenteredRect`, которые берут рабочую область.

**Настройки теперь обычный файл, и раньше им не были.** Они шли через `CFPreferencesCopyAppValue`,
который обслуживается из кэша `cfprefsd`: запись `local.eyeleo.EyeLeo.plist` через `plistlib` его не
сбрасывала, и файл на диске содержал новое значение, пока свежий процесс сообщал старое. Симптом
выглядел ровно как сломанное чтение, и то, что `killall -u $USER cfprefsd` его убирает, и доказало,
что с кодом всё в порядке. Теперь это `~/.config/eyeleo-mac/settings.xml`, который читается и пишется
напрямую, так что правка файла работает и кэша перед ней нет.

**Панель задаёт размер своей картинки один раз, по рамке, с которой открылась анимация.** Короткий
перерыв создаёт панель, берёт рамку у того, что анимация показывает в этот момент, и дальше только
подменяет картинку. Поэтому упражнение, чей начальный кадр другого размера, рисовало последующие кадры
не в ту рамку — масштабированные или обрезанные, и ничто в трассировке об этом не говорило. Это
случилось по-настоящему: у упражнения с плечами не было ветки в инициализаторе анимации, срабатывал
унаследованный нарисованный голова, и на настоящие кадры переключение происходило лишь на первом тике.
Панель трассировала `156x98` — унаследованную голову — перед кадрами `138x110`. Теперь и кадр, на
котором открывается, и каждый последующий берутся из одной таблицы в `ebexercise.m`, а проверка
обходит эту таблицу по поставляемым файлам и падает, если любые два кадра цикла расходятся по размеру.
Падает с размерами в сообщении — так правка была подтверждена, а не принята на веру.

**Преобразование — не то, что глаз читает как движение.** Стоит сохранить из версии, которую оно
заменило: поворот головы вокруг собственного нижнего края при одновременном подъёме отдельного торса
читался не как растяжка, а как разваливающийся монтаж. Переключение между двумя согласованными позами
читается именно как движение. Те же панели, которые нельзя было убедительно сдвинуть кодом, нельзя было
и убедительно перерисовать, и ответ оказался в инструменте.

## Сознательные отличия от оригинала Windows

- **Определение активности и полноэкранных приложений не требует разрешений.** Разобрано выше; это
  главный выигрыш порта.
- **Уведомления — собственные пузыри**, а не системные, чтобы не требовать разрешения Notifications.
- **Журнала нет.** Оригинал писал каждое изменение состояния в `log.txt`, переоткрывая файл каждый
  раз. Вместо него используется `os_log` — только для настоящих проблем.
- **Нет установщика.** У NSIS, `.manifest`, на который он ссылался, и DLL среды MSVC здесь нет
  эквивалента. `make install` копирует подписанный ad-hoc бандл в `/Applications`, и это вся раздача:
  ни `.dmg`, ни пакета, ничего монтировать не надо.
- **Нет `config.xml` в рабочем каталоге.** Оригинал брал оттуда язык и версию — относительно
  каталога процесса, из-за чего запуск откуда угодно ломался. Теперь язык следует за системой, а
  ресурсы живут в бандле.
- **Единственный экземпляр по идентификатору бандла.** Оригинал использовал именованный мьютекс Win32.
- **Правило русского множественного числа исправлено.** `getSecondStr` проверял `n/10 != 1` там, где
  правило требует `n%100 != 11`, из-за чего числа вроде 21 и 101 выводились неверно. Порт реализует
  настоящее правило и сохраняет исходные формулировки; `tools/check_strings.m` печатает их для осмотра.
- **Демонстрационный перерыв сохраняет странное правило оригинала.** `demo && strictMode`
  (main.cpp:776) означает, что кнопка «попробовать длинный перерыв» в настройках даёт полноценный
  перерыв, если тревожный режим выключен. Сохранено, а не тихо исправлено, и закрыто проверкой.

## Размеры экранов и несколько мониторов

В раскладке нет ничего, жёстко привязанного к разрешению. Каждый оверлей считается от дисплея в момент
показа, в пунктах, так что один код покрывает и MacBook Air 1280x800, и 5K Studio Display, и всё между
ними.

Задействованы две координатные системы, и путать их — это ровно то, чем оверлей оказывается под доком:

- `NSScreen.frame` — весь дисплей, вместе со строкой меню и доком. Его используют слой затемнения и
  экран длинного перерыва, потому что они должны закрывать дисплей от края до края.
- `NSScreen.visibleFrame` — рабочая область, кадр без строки меню и дока. Всё, что плавает над рабочим
  столом, центрируется или прибивается внутри неё: панель короткого перерыва, пузырь с отсчётом, диалог
  «перед перерывом», уведомление, баннер ожидания.

На этой машине (1470x956 при @2x, док 60 pt) эта разница стоит 13,5 пункта: по центру `frame` панель
садилась низко, у самого дока, по центру `visibleFrame` — в середину рабочей области.

Retina не проблема. Раскладка везде в пунктах, иконки строки меню поставляются с `@2x`, графика рисуется
в своём естественном размере в пунктах, так что леопард 156x98 пунктов будет 156x98 на любом дисплее.

При нескольких подключённых дисплеях:

- каждый дисплей получает свой слой затемнения, так что весь рабочий стол перекрыт;
- содержимое панели выводится на дисплей 0, основной, во всех трёх оверлеях перерывов.

Второй пункт — сознательное расхождение. Оригинал создавал `MiniPauseWindow` на каждый
не-полноэкранный дисплей, так что с двумя мониторами получалось две панели и приходилось решать, в
какую кликать. Одна панель на основном дисплее предсказуема; цена — перерыв, показанный, когда вы
читаете внешний монитор, появится на встроенном.

Ещё две защитные детали: если рабочая область дисплея меньше панели, панель и всё внутри неё уменьшаются
пропорционально, а не свисают за края; и изменение параметров дисплея — смена разрешения, перестановка,
подключение монитора, появление или скрытие дока — уничтожает все оверлеи, чтобы ничего не осталось
зависшим не того размера.

`NSWindow.frame` — свойство только для чтения. Чтобы переместить или изменить размер окна, используйте
`setFrame:display:`.

## Тесты

В оригинале их нет. Автомат состояний — это место, где порт тихо съедает перерывы пользователя, поэтому
он и покрыт: полный цикл перерыва, пауза и возобновление, автоматический отдых, блокировка полноэкранным
приложением и тревожный режим, путь отказа, продолжение после перезапуска, круг и обрезка настроек, а
также правила множественного числа. `tests/ebdetect_stub.c` подменяет определитель на CoreGraphics,
чтобы тесты шли без оконного сервера. `tools/smoke.sh` добавляет 19 сквозных проверок собранного
приложения, так что оверлей, который так и не появился на экране, роняет сборку, а не только юнит.

## Происхождение

Исходная Windows-версия Александра Гарустовича распространяется под CC BY-NC 4.0; полный текст —
в [`LICENSE`](LICENSE). Её графика, формулировки и поведение переиспользуются здесь под этой лицензией,
поэтому эта сборка некоммерческая и обязана сохранять указание на автора. `Resources/` начинается как

все сосуды для чая сгенерированы для этого порта инструментом `tools/mkframes.m` и покрываются той же
лицензией. Русские переводы четырнадцати формулировок упражнений, которых в оригинале не было, написаны
для этого порта; остальной русский текст — исходный.
